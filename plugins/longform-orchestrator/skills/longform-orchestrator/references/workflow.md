# Workflow detail

## The driver

`orchestrate --drive --live|--mock --execute [--request-id <id>] [--max-minutes N]` is the normal way to move work forward; it replaces hand-written polling loops. It serves the requests this host submitted (a named untagged or operator-owned request too; never another agent host's, `REQUEST_OWNED_BY_OTHER_HOST`), and only calls the normal advance, so every gate applies exactly as in a manual `--advance`: question scopes, request and provider pauses, recovery rules, write claims and the one admission path. It never answers a question, clears a hold or pause, reconciles or grants anything. It runs at most one advance per project at a time, up to the execution slots, the least recently served first, and uses a freed slot as soon as an advance ends, so every project gets service. After each advance it compares what the request's view shows (each task's status, specification, holds, pending rework, proposals, latest work, review and checks; the request's status, pause, open questions and Astra's checkpoint): a change means it advances that request again; no change means it looks at why. The reset of a provider pause the request is actually held by is waited for, in sleeps of at most a minute with every request read again between them; capacity, another run in the project, a write-claim conflict, another host's live process or a recheck elsewhere is retried with backoff (30 seconds, doubling to 10 minutes); anything else (questions, owner decisions, reconciliation, budgets, held pauses, a write conflict with an unknown run or an uncertain Drive write, slots held only by unknown runs) is not retried until something it tracks changes or the run or filing named in the refusal lets go. With only such blockers left, or at the time budget (default 50 minutes; a whole number from 1 to 600), it returns each request's `outcome`, `detail`, any `until` and `nextActions`. The budget is checked between advances: an advance under way finishes and is recorded. The driver owns no run custody and does not return while any advance is still active. If an in-flight lease expires, it reports an urgent warning while keeping the live host lock and database open until the advance truly settles. While it runs it appends progress lines to `driver.log` beside the database (`--log-file PATH` to change; the result's `logFile`): each advance, each run starting and finishing, the watchdog's notices, and after five quiet minutes what each request is doing. That file is for the owner to watch; do not read it into the conversation unless the owner asks.

When a run's heartbeat lease expires, the driver holds the request as `RUN_LEASE_EXPIRED`, with the run/task identity and the operator's next step, and says so on stderr at once. A lease timestamp is not proof that the process stopped or that external effects are absent; never replay it blindly. A run that is not this process's is left alone: the hold names `longform-orchestrator resume --execute`, which checks **all** expired attempts in the shared database (inspect that scope first), then `reconcile-helper --run-id RUN`, verified evidence and `reconcile` for a started attempt. A run this process's advance still waits on is asked to stop, scoped to it (as a lost lease stops any run); the driver does not return, and the CLI keeps its live host lock and open database, until the controller ends that advance: when the adapter confirms the stop, or, after a 30-second grace, when no process of the run is alive by the runner's own records and no Drive write of it is open, in which case the run is recorded `RUN_STOP_UNCONFIRMED` and UNKNOWN, with its claims, for reconciliation (`reconcile-helper --run-id RUN`, then the operator's own checks, evidence and `reconcile`). While a process or a Drive write of it may be alive, or the adapter cannot say, the driver keeps waiting, says so, and asks again. Before the driver returns, and before any live `orchestrate` command releases its host lock and closes the database, the CLI waits until no sandbox process of this process's runs is alive and no Drive write begun here is still open, saying what it waits for on stderr; an adapter's bounded cancellation can end an advance while the runner is still stopping, and that wait covers it. The watchdog never releases a claim, invents a receipt or starts anything.

## A request at a glance, pauses and reconciliation drafts

`orchestrate --request-id <id> --compact` is the routine status view: status, a count of tasks by status, open owner and operator questions with their scope, each hold with what it means, what clears it, the command and whose authority it needs (a command shown grants nothing), provider pauses, the request's own pause, runs in progress and next steps.

The owner may pause a request (`--pause --file` with `{"text","sourceRef"}`, the owner's words). A run already going finishes and its result is recorded; every reservation for that request is refused (`REQUEST_PAUSED`) in the same transaction as admission, and a run reserved before the pause is not started; other requests, and the paused request's project inputs, are untouched, so nothing is invalidated. The view's status is `PAUSED`. `--resume` (same shape, again the owner's words) lifts only the pause.

`reconcile-helper --run-id <run>` (read-only) drafts the envelope for reconciling an unknown run from its attempt, receipt or rejected observations, the runner's run record, its Drive calls and writes, open write intents and observed usage. It leaves `processStopped`, `externalEffects` and, when none was observed, `usage` as null, with `mustConfirm` saying what to check and `cannotEstablish` what the controller could not see. Fill them only from your own checks.

## Routing

Use `plan` or `route` and inspect the active trusted routing policy. With `ASTRA_TWO_TIER`, Sol 6.1/high assesses difficulty; Complex uses Sol 6.1/xhigh with Opus 5.5/high reviewing, Expert uses Sol 6.1/max with Opus 5.5/xhigh reviewing. Ordinary code may start Complex; high stakes (protected documents, code paths, owner decisions, an `expert` work type, or what the assessor finds) set an Expert minimum. Two failed Complex reviews raise the next worker and its reviewer to Expert, the ceiling; failed checks don't count. The review follows the exact artifact's worker tier. A task Claude already worked on before the switch keeps that pairing: Opus 5.5 reworks it (high for Complex, xhigh for Expert) and Sol 6.1 reviews it (xhigh, max); Astra's oversight and advice do not count as authorship. Never supply model flags or substitute models. Historical policies stay readable but are not the current configuration.

## Astra's oversight

Astra/xhigh oversees the explicitly linked project through saved checkpoints: it validates the plan, selects the next tasks, gives assignments, checks changed results and gives final technical sign-off. On resume, read the response's `project` summary (Astra's latest plan, each task's status and holds, the questions); add `--project-full` only when you need the whole record, which is large. Model plans are guidance; current source records and owner instructions win. A missing, invalid or unknown checkpoint, changed project inputs or an unassigned task holds dependent work; show concrete `PROJECT_OVERSIGHT` held-step details when it cannot run. Astra's sign-off cannot waive failed reviews, checks or tests, change scope, make owner decisions, accept work or release it.

## Pre-design decision discovery

A task record that names `preDesignDiscovery` (`policy` `REQUIRED`, `AUTO` or `EXEMPT`, with `rationale` and `sourceRef`; see `task-records.md`) is screened by Astra before its first worker run, when the policy or the deterministic classifier says the work is consequential (a design work type, high risk, an owner decision, changes to existing documents, cross-task dependencies or shared resources, expert complexity, or an unknown work type); a fix task, routine filing or an owner brief under `AUTO` is exempt with a recorded reason and no model call. Astra finds the choices only the owner can make and the controller turns each into an `OWNER_DECISION` question (`pre-design-question:…`, recommendation first, 2–4 answers, the tasks that wait) in the same advance; the affected tasks wait, the others continue. The request view shows each opted-in task's state under `project.tasks[].preDesign` and the hold in `holds`. The worker is admitted only on a current screening whose questions are answered; the answer is context for the work, never a grant or a change of scope. A screening goes stale only when the task's own specification, a related task's specification, the owner's decisions on it or the specification of a task its question holds changes; then Astra screens it again on the next advance. Nothing here gates a task without the field.

## Difficulty assessment

The task view shows `difficulty`. When no assessor could assess a task, relay the hold with three answers: 1) try again (recommended for a transient failure), 2) proceed on the fixed stakes alone, 3) leave it held. Record the owner's actual choice with `assessment`; never choose for them.

## Checks and failed reviews

Checks (and required tests) run after each successful worker run, before any review. When one fails, the view shows `rework` with `verdict: "CHECKS_FAILED"` and the problems; advance again and the worker fixes its work in place, by the same provider, from the sealed work; the checks then run again. A check that could not run holds the task (`WORKFLOW_CHECKS_HELD`).

After a failed review, advance again: the worker fixes its work in place with the review's must-fix items, and a fresh review checks the result. Revise the task only when the specification itself must change (for example to fold in the owner's answer); record the grant for the revision and rebind it, and the worker starts afresh.

**Macro audit validity after other tasks change.** For new worker runs, the macro audit goes stale only when a related task changes (a dependency or the task it fixes, a task sharing a named resource, a code task targeting overlapping paths of the same repository) or when another task's run or filing actually writes a Drive file the work read, listed, updated, created or binds as a source, after the run began. Another task's grant, status or Drive scope alone no longer counts. Missing Drive records count against the work, never for it. A real overlap is a hold: verify it, then record an exact run-bound `drift-ack`; that is the operator's reconciliation, shown on the audit as `acknowledged`, not a new model assessment. Audits and acceptance on older runs keep their original whole-project rules. Do not declare overlapping Drive edits harmless by assumption or erase any historical FAIL.

## Proposals and the moderator

The first review of a specification may propose better ways to do the work (not for a work type without proposals, such as `records`). The worker answers each proposal in one more run, the moderator sorts what is still open, and the rest becomes an `OWNER_DECISION` question (key `proposal-question:…`). `READY_FOR_PROPOSAL_ROUND` means advance again. Relay each proposal question framed as what the user would see or feel, the moderator's recommendation first when it has one, and record the reply in words. If the owner chooses the reviewer's change, revise the task, record the grant and rebind; if the owner keeps the work, advance. Proposals never block a pass; verification waits only until every proposal is settled.

## Owner and operator questions

Each question is for the owner or the operator and declares the tasks that wait for it (`taskIds`) or `projectWide`. The request status is `WAITING_INPUT` only when a project-wide question is open or every open task waits on one; otherwise the other tasks advance, and `nextSteps` says some wait on questions. Relay owner questions to the owner. Answer operator questions (Astra's `ASK_OPERATOR` questions and workers' `QUESTIONS FOR THE OPERATOR:`) from the controller's records with `answeredAs: OPERATOR` and `evidence`; when the records do not settle one, say so in the answer or ask the owner a proper question. The view's `operational` section (and `--compact`) lists holds, runs awaiting reconciliation and what clears each; check it before asking anyone.

**Optional informational follow-ups.** Never silently dismiss a question because the worker or Astra calls it optional. Only a recorded OWNER-authorized, task-scoped INFORMATION question can be deferred through `orchestrate --request-id R --defer-question-file FILE --execute`. The file must name the exact question ID and text, the owner's actual direction, a reason, and the conversation source. A deferral is an append-only, non-authorizing disposition (not an answer); Astra's project snapshot and task briefs retain it as DEFERRED. Actual OWNER_DECISION, ACCESS, SCOPE, project-wide and reserved worker/proposal/Astra questions cannot be deferred using this path. Rebind a revised specification separately after the remaining binding questions are answered. Cross-request questions remain binding even while the project's task spec is awaiting rebind.

**Old questions after an authorized task revision.** The answer file can explicitly include `"historicalOnly":true` with `"answeredAs"` **only** for a question whose bound task specification no longer matches: `"OWNER"` with the owner's actual answer for an owner question, or `"OPERATOR"` with `evidence` for an operator question (for example, an operator question about a task that was then revised). This closes the old question without claiming it applies to the revised specification or granting any new authority; the historical label covers only the revised tasks, and for a covered task whose specification is unchanged the answer is an ordinary one. Normal stale-spec answers still fail, and an operator can never answer an owner question this way. All revised-task permission and review gates remain mandatory before separate explicit rebind. Treat this as a historical disposition, not proof a domain owner adopted a new rule.

## Provider usage limits

A run cut off by its provider's usage limit pauses that provider for every role until its stated reset (or a recheck interval); it counts as an attempt but not as failed work, and the next attempt at the same step resumes its files. The request view's `providerPauses` and next steps say when. Work on the other provider continues; Astra's checkpoints are never moved to Claude, so work that needs one waits while Codex is paused. A held provider, or a step cut off three times, needs the owner's word (`provider-pause --clear` with evidence, or `retry-extend`). `provider-limits --scan` lists earlier receipts that hit a limit, read only. Detail: `docs/live-runner.md`, "Provider usage limits".

## Write claims and uncertain Drive writes

Runs and filings that would write the same Drive file, create in the same folder or share an explicit resource wait for each other (`CLAIM_CONFLICT`); similar-looking local write paths do not, since each run writes its own workspace. A Drive write whose outcome is unknown (`DRIVE_WRITE_UNCERTAIN`), or a filing that stopped while holding its claims (`FILING_CLAIMS_UNCERTAIN`), holds its files until the operator checks Drive and records it with `claims-reconcile` (at least ten minutes after the write and the stop; a stopped filing's stop counts from when `claims-reconcile` first sees it gone, so the first call may answer `CHECKED_TOO_EARLY` with the time to check after). `claims` shows who holds what. Detail: `docs/live-runner.md`, "Write claims".

## Runs that never launched

A worker refused, cancelled or timed out before launch (a pack that could not be fetched, a failed Drive login, an unattested route) used nothing: no attempt, the earlier sealed work stays current, and the view shows `WORKER_NOT_LAUNCHED:<reason>` until a run launches. Fix the cause or advance to retry. A run the operator cancelled stays cancelled.

## Long conversations

The controller keeps every request's whole state, so the conversation need not. Before registering, revising or rebinding a long task, run `brief-preview TASK --request-id <id>` (or `--file <record>` for a task not yet registered or a revision; read-only) to see each role's complete brief size; when the owner's request text cannot fit a brief, the run gets it whole in a read-only owner-text file and is told to read it first. A run refused with `PROJECT_CONTEXT_TOO_LARGE` spent nothing and left nothing waiting; finish the phase and continue the remaining work as a new request under a new project key.
